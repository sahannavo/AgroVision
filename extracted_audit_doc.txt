The agent only reads the repository and writes a report; it never changes anything. How to use this Run the audit on your own machine in the same repository (the lead&apos;s clone), after the latest work is merged: git fetch --all --prune, then git checkout dev, then git pull. Install the GitHub CLI (gh) and sign in, so the agent can read pull requests and branch protection. Start a new agent. Paste the common rules block first, then ONE audit prompt (A, B, C, D or E). For a full check, paste the common rules and the master prompt. For audit B, run it once per member (type their initials where the prompt says so) so each report stays short. Start with the members whose screens look suspicious. Do not let the agent fix things. Read the report, check three or four findings yourself with the evidence it gives, and then send each member only their own list. Members fix their findings on fix/&lt;short-desc&gt; branches with a pull request, as usual. Run the audit again before you tag v0.2-backend. Run the manual checks at the end of this document on a real phone: an automated audit cannot see everything. The team of eight finished the front end (Phase 2) against the plan in the team&apos;s sprint document, and the lead needs to know what is really in the repository. RULES FOR THE WHOLE AUDIT 1. Read-only. Do not edit, delete, move, format or commit anything. Do not run git commands that change history or the working tree (no commit, merge, rebase, reset, clean, push, stash, checkout of files). Switching to the dev branch and pulling is allowed: run git fetch --all --prune, then git checkout dev, then git pull. 2. Evidence for every finding: file path and line number, or commit hash, or the exact command output. If you cannot prove it, do not report it. Never guess who is at fault: use git log and git blame and say which commit. 3. Give every finding a severity: BLOCKER (the app does not build, a screen is missing or a stub, a secret is committed, a merge conflict marker is present), MAJOR (breaks a rule in the plan or the design, a wrong owner edit, duplicate code), MINOR (style, naming, small junk). 4. Name the owner of the file from the ownership list in the team&apos;s file structure document (and CODEOWNERS if it exists), and the commit author, because they can differ. 5. If a check cannot be done (no gh CLI, no Flutter, no emulator), say so in a &quot;Could not check&quot; section instead of skipping silently. 6. Be fair: report facts, not blame. Do not judge people by commit counts. 7. Output in the report format given in the last section. Keep the output short where nothing is wrong (&quot;No issues found: checked N files&quot;). Audit E: code quality and architecture rules AUDIT E: Code quality and architecture rules. Goal: check the code against the rules the team agreed on. 1. Tooling. In app/: dart analyze (list every issue by file), dart format --output=none --set-exit-if-changed . (list unformatted files), flutter test (list failures) and coverage if available. Report which screens and widgets have no test. 2. Theme rules. Search lib/features and lib/core/widgets for colour literals (Color(0x, Colors., hex strings), text sizes (fontSize:), font families, radius numbers (BorderRadius.circular with a literal) and spacing numbers that should come from AppColors, AppTextStyles, AppRadius and AppSpacing. List file, line and the matching token if one exists. 3. Layering. Presentation files must not import Firebase packages, repository implementations or fake repositories; they read data through providers. Domain files must not import Flutter widgets or Firebase. List violations. 4. Size and structure. Files over 300 lines, files with more than one screen or public widget, widgets that are defined inside a screen file but used in two or more features (they belong in lib/core/widgets), and shared widgets in lib/core/widgets that only one feature uses. 5. Flutter quality. List: controllers and subscriptions that are not disposed (TextEditingController, ScrollController, AnimationController, CameraController, StreamSubscription); use of BuildContext after an await without a mounted check; Row or Column children with long text and no Expanded or Flexible (overflow risk); ListView inside Column without a bounded height; images without errorBuilder or placeholder; setState-heavy screens that should use providers; build methods that start network or camera work; missing const constructors where analyzer suggests them. 6. Accessibility. IconButtons and icon-only controls without a Semantics label or tooltip, tap targets smaller than 48 dp, text that ignores text scaling (fixed heights around text), and low-contrast colour pairs from the theme (compute the contrast ratio for text on its background and list pairs under 4.5). 7. Offline and states. For each screen, list which states exist (loading, empty, error, offline) and compare with the designs. List screens that can show a blank screen or an unhandled exception when a provider returns an error. 8. Scope. List features present in the code that are not in the designs or the project scope (phone login, OTP, PIN, language buttons, field tools, harvest advisory cards) and anything the designs require that is missing. 9. Strings and data. Repeated hard-coded strings that should be shared, magic numbers without a named constant (the 70 percent confidence threshold must be a named constant), and sample data outside the fake repositories.
