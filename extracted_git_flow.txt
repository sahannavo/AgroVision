The short answer The branch names in the prompts (feature/ui/auth and similar) were only a suggestion, so they are not important. You can keep one personal branch per member. What matters to the lecturer, and what protects your code, is this: Everything reaches dev through a pull request with a reviewer, not by pushing. Commits are small, regular, and made by the person who owns the files. Nobody merges other people&apos;s personal branches into theirs. The duplicate widgets in the audit (home, history, advisor) came from exactly that: branches merged into each other. Each task has its own pull request, so the history shows what was finished and when. A personal branch is good for attribution: &quot;kaveesha&quot; with 52 commits shows exactly who did what. The risk is only a branch that is never synced with dev and merged all at once at the end. Never merge &quot;frontend&quot; or another member&apos;s branch into yours. One task, one pull request. When a task from your document is finished and its tests pass, open a pull request from your branch into dev. Title: &quot;[Area] Task name&quot;, for example &quot;[Func] Weather functions and repository&quot;. Use the template, link the issue, and ask your review partner. Do your tasks one after the other. Finish and open the pull request before you start the next task, otherwise one pull request mixes two tasks. If you really must work on two things at once, make a short branch for the second one from your own branch. Keep pull requests small. If a task is large, open the pull request in two or three parts, after each group of commits. Merge method: &quot;Create a merge commit&quot; or &quot;Rebase and merge&quot;. Never squash. No force-push, and no rebase of commits that are already pushed. If a pull request shows conflicts: merge dev into your branch on your machine, keep the other person&apos;s version of any file you do not own, run flutter analyze and flutter test, push, and then merge the pull request. Do not delete your branch before the submission. It is evidence of your work. After a pull request is merged, you continue on the same branch (after merging dev again).
